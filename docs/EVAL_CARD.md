# CulinaCompass SG: Eval Card

How the agent is tested, what each number means, and how to reproduce every row. Companion to `DATA_CARD.md` (the data) and the report, `docs/REPORT.docx` (the interpretation).

## 1. What is being tested

Whether a planner, given a free-text request from a South Indian home cook in Singapore, (a) identifies the dish they **named**, (b) respects their diet, equipment and budget, (c) adapts when the dish can stay recognisable and abstains when it cannot, and (d) never overclaims what is in stock.

## 2. Scenarios

| File | What it is |
|---|---|
| `eval/scenario_seeds.jsonl` | 32 hand-written requests with target dish and constraints (original wording) |
| `eval/scenario_seeds_paraphrased.jsonl` | The same 32 scenarios reworded in natural code-mixed English ("palli", "kaju", "mixie", "plant-based", "five dollars") |
| `eval/scenarios.jsonl`, `scenarios_paraphrased.jsonl` | Seeds plus ground truth, generated by `eval/make_scenarios.py` |

Ground truth is **derived by code**, never typed per scenario: forbidden ingredients, signature ingredients, required flags, acceptable substitutions and the expected outcome all come from the data tables, `culinacompass/rules.py`, and the 46 human-labelled substitutions. The outcome policy is written at the top of `make_scenarios.py` so it can be argued with.

The 32 scenarios break down as 8 `adapt`, 19 `adapt_with_caveat` and 5 `abstain_and_explain`. They are tagged by trap type (signature conflict, equipment gap, hidden gluten or dairy, alias collision, budget conflict, lazy trap, false-alarm trap and others). Run `python3 eval/make_scenarios.py` to regenerate.

## 3. Metrics (`eval/score.py`)

Reported separately on purpose, with no single headline number.

| Metric | Meaning |
|---|---|
| `constraint_adherence` | No forbidden ingredient used; missing equipment and budget overruns flagged. Abstaining passes trivially, so read it beside fidelity. |
| `dish_fidelity` | Plan is for the dish the user named, the adapt or abstain decision matches ground truth, and every signature ingredient is kept or replaced by an acceptable substitute. |
| `task_success` | Adherence **and** fidelity in the same scenario. The headline metric. |
| `substitution_acceptability` | Share of proposed substitutions labelled acceptable. Unlabelled pairs are "unjudged", never counted as passes. |
| `flag_recall` | Share of must-flag ingredients (Difficult, Unknown, label-dependent) the planner flagged. |
| `availability_overclaims` | Count of "Confirmed" claims the data does not support. |
| `false_alarms` | Flags on ingredients that needed none. |

## 4. Planners and inputs

| Planner | What it is |
|---|---|
| `rules` | No-LLM baseline: keyword parser plus rule planner. Parser frozen by hash (`eval/rule_parser.frozen.sha256`) before the paraphrases were written. |
| `agent` | LLM with tool calling, plus the code validator loop. Model set by `--model` or `OPENROUTER_MODEL`. |
| baselines `lazy_safe_dish`, `as_written` | Degenerate planners that bound the metrics (always plain dosa; ignore all constraints). |

`--input text` gives only the request text (constraints must be inferred). `--input profile` also gives structured constraints. **The dish is never handed to either planner.**

### Prompt versions

- **v1:** the original system prompt in `culinacompass/agent.py`.
- **v2:** v1 plus one sentence: when abstaining because a signature ingredient is blocked, still submit the named dish's `dish_id` (null only when no supported dish matches). The `submit_plan` tool description in `tools.py` carries the same clarification.

Why: on v1, qwen abstained correctly on S13P, S26P and S28P but submitted `dish_id: null`, so the scorer recorded "no dish addressed". `agent_qwen_fix_check` is a 3-scenario diagnostic that confirmed the fix before the full runs.

## 6. Run files (`eval/runs/`)

Each run writes `<name>.outputs.jsonl` (what the planner returned), `<name>.details.jsonl` (per-scenario pass or fail and why), `<name>.summary.json` (the metrics plus token usage) and, for agents, `<name>.trace.jsonl` (every tool call). Wording in `details.jsonl` such as `addressed_target: false` is the quickest way to see why a scenario failed.

## 7. Reproduce

```bash
python3 eval/run_eval.py --planner rules --input text --set paraphrased       # free, ~1 s
python3 eval/score.py --baseline lazy_safe_dish                              # free
python3 eval/run_eval.py --planner agent --input text --set paraphrased \
        --model qwen/qwen3.7-flash --name my_run                              # ~US$0.03, needs an API key
python3 eval/run_eval.py --planner agent --input text --set paraphrased --no-validate   # validator ablation (not yet run)
```

Agent runs are not bit-for-bit repeatable even at temperature 0 (no seed, provider-side routing); expect about three scenarios of swing between runs.

## 8. Limitations of this eval

1. **Not held-out for the LLM.** The paraphrased set was written after the rule parser was frozen, so it is held-out for the *baseline*. The v2 prompt was derived from failures on this same set, so the v2 numbers are optimistic. A fresh unseen set is needed.
2. **Small.** 32 scenarios, so one scenario is about 3 points. Run-to-run variation on qwen reached 12.5 points.
3. **Not like-for-like.** gpt-5-mini was run once, on v1.
4. **Ground truth is the author's policy.** Substitution labels come from one reviewer, so the eval measures agreement with that judgement.
5. **Ablation not run.** The contribution of the validator loop is unmeasured.
6. **Snapshot data.** Evidence is from 2026-09-28 and online catalogues only (see `DATA_CARD.md`).
